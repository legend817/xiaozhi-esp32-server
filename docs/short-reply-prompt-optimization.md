# 短问短答 Prompt 优化记录

## 目的

短语音基线显示：服务端“说完到首音频”已经接近 1.9s，但“播放完成”仍经常超过 10s，主要原因是短问题触发了较长回答，导致 TTS 播放时间变长。

本优化目标不是降低 LLM 首 token，而是降低回答长度，从而减少 TTS 总播放时间。

## 已应用对象

- 智能体：`test`
- 表：`ai_agent`
- 字段：`system_prompt`
- 标记：`SHORT_REPLY_OPTIMIZATION_V1`

## 追加规则

```text
[响应速度优化 SHORT_REPLY_OPTIMIZATION_V1]
- 默认回答控制在1到2句，先给结论，不铺垫。
- 对"你是谁"、"现在几点"、"在吗"这类短问题，回答不超过15个汉字。
- 用户要求讲故事、解释原理、列方案时，先说第一小段，再问要不要继续。
- 不主动扩展背景，不连续举例，不重复用户问题。
- 能用一句话答完时，绝不说第二句。
```

## 应用方式

通过 MySQL 直接追加到 test 智能体 `system_prompt`，并使用 `SHORT_REPLY_OPTIMIZATION_V1` 做幂等标记，避免重复追加。

应用后需要重启 `xiaozhi-esp32-server`，否则进程内 prompt 缓存可能仍使用旧规则。

## 回滚方式

如果需要回滚，建议在管理后台编辑 test 智能体提示词，删除从 `[响应速度优化 SHORT_REPLY_OPTIMIZATION_V1]` 开始的整段规则。

也可以用 SQL 回滚，但需要先人工确认 prompt 内容，避免误删用户后续手动修改。

## 复测结果

样例：`docs/perf-baselines/audio/ni_shi_shei.wav`

| 指标 | 优化前 P50 | 优化后 P50 | 变化 |
| --- | ---: | ---: | ---: |
| ASR | 910ms | 956ms | 基本持平 |
| LLM 首 token | 542ms | 608ms | 略慢，样本较少 |
| TTS 首音频 | 994ms | 1025ms | 基本持平 |
| TTS 首音频到结束 | 14990ms | 4824ms | 明显下降 |
| 组合完成 | 16778ms | 8947ms | 约快 7831ms |

## 结论

短问短答约束对首音频帮助不大，但能显著降低播放完成时间和用户等待整段播完的体感。

下一步如果继续优化首响应，应转向 ASR：对比 `FunASRServer` 或流式 ASR。
