# 企业客服 RAG 优化计划

## 背景

目标场景是企业客服/企业信息问答，不是电商售后客服。

典型问题：

- 公司主要做什么
- 产品有哪些
- 价格/套餐是多少
- 怎么合作
- 联系方式是什么
- 有哪些客户案例
- 企业资质、合同、发票、服务流程

这些问题多数需要依赖企业知识库，不能让 LLM 凭空编答案。因此 RAG 的真实耗时会直接影响语音体验。

## 当前决策原则

先测 RAG 真实耗时，再决定是否做“两段式回答”。

不先凭感觉改交互。

## 2026-07-29 实测结论

当前 test 智能体使用：

- Intent：`Intent_lightweight_router`
- LLM：`Qwen3-30B-A3B`
- ASR：`ASR_FunASRServer2Pass`
- TTS：`TTS_HuoshanDoubleStreamTTS`
- RAG：RAGFlow，知识库 `中科生创公司信息`

问题：

```text
中科生创公司是做什么的？
```

阶段性结果：

| 方案 | chat_end | TTS 首音频 | 关键特征 |
|---|---:|---:|---|
| `Intent_function_call` 原始 RAG | 5574 ms | 5697 ms | LLM 先判断工具，再查 RAG，再二次 LLM |
| `Intent_lightweight_router` 小工具集 | 4578 ms | 4938 ms | 只暴露 `search_from_ragflow` 与 `direct_answer` |
| 轻量路由确定性 RAG | 3477 ms | 3633 ms | 后端直接调用 RAG，省掉第一轮 LLM 工具决策 |
| 确定性 RAG + 检索参数收敛 | 2496 ms | 2602 ms | `page_size=3`、`top_k=16`、`similarity_threshold=0.3` |
| 高频问题命中 RAGFlow 上下文缓存 | 1114 ms | 1196 ms | 省掉 RAGFlow `/retrieval` 请求，仍保留一次 LLM 总结 |

结论：

- 当前 RAG 检索本身约 0.8～1.1 秒，暂不需要 staged RAG。
- 最大收益来自绕过第一轮 LLM 工具决策，以及减少 RAG 返回上下文。
- 高频重复问题命中 RAGFlow 上下文缓存后，RAG 工具耗时从约 1000 ms 降到个位数毫秒，首音频进入约 1.2 秒。
- 企业信息问答可以先采用“等 RAG 后直接回答”，不需要先播“我查一下资料”。
- 如果后续知识库变大或 RAGFlow 检索超过 1500 ms，再启用 staged RAG。

当前默认策略：

```text
轻量路由命中 enterprise_rag
  ↓
后端直接调用 search_from_ragflow(question=原问题)
  ↓
RAGFlow 返回少量高相关 chunk
  ↓
只做一次 LLM 总结
  ↓
TTS 播放答案
```

维护注意：

- 不要让 `enterprise_rag` 再走完整 function_call 工具决策链。
- RAGFlow 默认返回 chunk 不宜过多；语音客服优先短答案。
- RAG 插件默认参数可被插件配置覆盖：
  - `page_size`
  - `top_k`
  - `similarity_threshold`
  - `max_context_chunks`
  - `max_context_chars`
  - `cache_enabled`
  - `cache_ttl`
- 如果出现查不全，再优先调大 `page_size/max_context_chunks`，不要直接恢复到 30 个 chunk。
- RAGFlow 上下文缓存是精确归一化缓存，缓存键包含问题、知识库、RAGFlow 地址和检索参数；不同知识库或不同参数不会串用结果。
- 默认只缓存 RAGFlow 返回的上下文，不缓存最终 LLM 答案，避免知识更新后长时间复用旧话术。

## 候选交互策略

### 1. 直接回答

适用：

- 低风险问题
- 不依赖企业事实
- 例如“你能帮我了解公司吗”

特点：

- 最自然
- 不查 RAG
- 延迟最低

### 2. 缓存回答

适用：

- 高频企业问题
- 最近已经查过 RAG
- 缓存仍有效

特点：

- 体验最好
- 可以直接回答事实
- 后续应重点建设

当前已先落地较保守的“RAGFlow 上下文缓存”：重复问题会跳过 RAGFlow 检索，但仍让 LLM 根据缓存上下文生成回答。它比最终答案缓存慢一些，但事实串库和旧答案风险更低。

### 3. 等 RAG 后回答

适用：

- RAG 检索足够快

判断标准：

```text
RAG < 700ms
```

特点：

- 不需要先说“我查一下”
- 体验仍然自然
- 答案可靠

### 4. 两段式 staged RAG

适用：

- RAG 检索明显慢

判断标准：

```text
RAG > 1500ms
```

流程：

```text
用户提问
  ↓
立即播短确认：我看下资料，给你准确说法。
  ↓
后台并行查 RAG
  ↓
RAG 返回后生成短答案
  ↓
第二句无缝接上
```

原则：

- 第一短句不能编企业事实
- 第二句必须基于 RAG
- 查不到时明确说资料里没查到

## 阈值建议

```text
RAG < 700ms:
  直接等 RAG，再回答

RAG 700ms～1500ms:
  先不做复杂两段式，可继续观察首音频体感

RAG > 1500ms:
  做 staged RAG
```

## 通用 RAG 质量策略

RAG 优化不能靠给某个企业、某个问题逐条写特例。后续导入新知识库时，仍然按下面的通用准入规则处理：

- 简单字段问答可以走直答快路径，例如电话、官网、总部地址、营业时间、单个负责人、单个数值。
- 复合问题不走短直答，例如“分别是谁”“有哪些”“具体包括什么”“详细介绍”“如何合作”“为什么”等。这类问题先检索 RAG，再交给 LLM 在当前回复预算内组织完整答案。
- 数量类问题只有在用户只问数量时才允许裁掉名单；如果用户同时问“分别是谁/有哪些”，不得裁掉名单。
- 直答缓存只缓存通过一致性校验的答案，并且缓存键必须包含 RAGFlow 地址、知识库 id、检索参数和直答阈值，避免新知识库串用旧答案。
- 答案进入 TTS 前要做通用文本规范化，例如电话号码中 `0591- 87699999` 这类分隔符空格要清理。
- 如果直答超过当前语音预算，必须回退到 RAG+LLM，而不是强行截断成半个事实。
- 长答案不是问题本身；问题是一股脑输出。RAG+LLM 的流式文本必须按自然标点分段进入 TTS，优先在 `。！？；` 断句，其次在逗号、顿号、冒号等软标点断开，避免把一大段文本一次性送给 TTS。
- 语音交互的目标是“首句尽快、后续按句推进、用户可打断”，不是单纯把所有回答压到很短。
- RAG+LLM 的企业回答第一句应是 30 个汉字以内的完整结论句，并带句末标点。这样首段可以更早进入 TTS，后续再按标点继续补充资料。
- 如果模型第一句仍然偏长，分段器第一段可以在约 28 个汉字处先送入 TTS，不必等到完整句号；后续片段继续按自然标点衔接。首段优先级高于句子完整性，但不能破坏事实含义。
- 已试验将首段上限降到 8 个汉字：后端分段生效，但火山双流可能合并过短片段，首音频没有稳定收益，且听感风险更高。因此默认恢复 28 个汉字，继续优先解决 RAG 首句来源问题。
- 对需要 RAG+LLM 综合的问题，可以启用 staged first reply：RAG 已返回有效上下文但不能直答时，优先从 RAG 命中的 Q&A 回答或普通段落里抽取一个短事实句先播，同时继续让 LLM 组织正式答案。
- RAG 首句抽取不必只等句号；逗号、顿号、冒号也可以作为自然首段边界。但不能硬截断无标点长句，避免播出半句话。
- 默认不使用固定过渡话术，避免每次首句都一样、显得像查询机器。只有配置了 `staged_first_reply` 时，才在无法抽取可信 RAG 首句时作为兜底话术。相关开关：`staged_rag_first_sentence_enabled`、`staged_first_reply_enabled`、`staged_first_reply`。

新知识库导入时，优先保证资料结构清晰：

- 高频 FAQ 用 Q&A 结构，问题字段放自然问法，回答字段放可直接播报的短答案。
- 需要解释的资料用普通文档或较完整段落，不要硬塞进一个超长 FAQ 答案。
- 同一个事实可以有多个问法，但答案文本要尽量一致，这样直答一致性校验和别名缓存才能命中。
- 不要把多个不相关事实放进同一个回答里，否则会降低检索准确率，也会拖慢 LLM 组织答案。

## 2026-07-29：企业 Q&A v3 导入方案

### 管理端与 RAGFlow 的职责边界

管理端知识库列表不是实时读取 RAGFlow 全部数据集，而是依赖管理端数据库里的知识库记录和 RAGFlow `dataset_id` 映射。因此必须按以下顺序操作：

1. 先在管理端创建知识库，确保管理端生成并保存映射；
2. 再到 RAGFlow 找到对应数据集，选择 `Q&A` 分块方式并导入文件；
3. 回到管理端给智能体绑定该知识库。

直接在 RAGFlow 新建的数据集不会自动出现在管理端，这是两个系统的数据同步边界，不是 RAGFlow 导入失败。

### v2 问题与 v3 修正

v2 把一个标准问题和多个别名用换行放在同一个“问题”单元格中。实测 RAGFlow 会把整格长文本作为一个问题参与混合检索，导致关键词权重被稀释：企业主营问题可能错误排在电话、科学家等答案之后；人名问题还可能被 `similarity_threshold=0.3` 过滤掉。

v3 改为：

- 每一种问法独占一行；
- 同义问法重复使用同一条标准答案；
- 共 336 条独立问法、43 条标准事实；
- 服务端按“回答正文”去重，避免同一答案的多个别名占满 3 个上下文名额。

导入文件：`docs/ragflow/identity.ragflow.qa-v3.xlsx`

审计文件：`docs/ragflow/identity.ragflow.audit-v3.xlsx`

推荐新建管理端知识库 `中科生创公司信息_QA_v3` 做并行回归，不覆盖 v2。RAGFlow 解析完成后应显示约 336 个 Q&A chunk；然后把 test 智能体从 v2 切换到 v3，保留 v2 作为临时回滚版本。

### v3 验收问题

至少回测以下类型：

```text
中科生创公司主要是做什么的？
中科生创公司的电话是多少？
中科生创公司的地址在哪里？
林晓锋是谁？
中科生创有多少位科学家，分别是谁？

```

每一条同时检查：路由是否命中 `enterprise_rag`、召回事实是否正确、是否出现重复答案、是否严格拒绝知识库里不存在的事实，以及冷/热缓存的 TTS 首音频耗时。

### 短人名受控检索

RAGFlow 对 `林晓锋是谁？` 的精确问法出现关键词相似度接近 0 的异常，统一阈值 `0.3` 会零召回。不能因此全局降低阈值，否则普通问题容易引入噪声。

当前只对严格的短人名问句启用 `entity_fallback_threshold=0.18`，并在服务端二次要求 chunk 正文必须包含完整姓名：

```text
林晓锋是谁？
  → 0.18 检索
  → chunk 必须包含“林晓锋”
  → 同答案去重
  → LLM 简短回答

马云是谁？
  → 0.18 检索
  → 无包含“马云”的 chunk
  → 企业知识库里暂时没有这位人员的信息
```

实测 `林晓锋` 检索 373 ms，3 个别名 chunk 去重为 1 个；知识库外对照人名无召回，不会串入其他企业事实。

## 高置信度 Q&A 直答快路径

标准 Q&A 经过 RAGFlow 检索后，原链路固定再请求一次 LLM。真实设备中该步骤通常增加约 600～800 ms。对于电话、地址、人数、人名等已有标准答案的问题，这次生成通常没有新增价值。

`search_from_ragflow` 现增加保守直答快路径，默认启用：

- 存储问题与用户问题完全一致时，可以采用其标准答案；
- 问法不完全一致时，至少两个召回 chunk 必须收敛到同一个答案；
- 竞争答案与首选答案分差小于 `0.03` 时回退 LLM；
- 召回相似度默认至少 `0.36`；
- “详细、全面、为什么、如何、对比、区别”等需要解释或综合的问题始终回退 LLM；
- 直答上限为 75 字，超长自动回退；
- 数量问题会去掉答案中未被询问的“分别为……”名单；
- 冷检索和热缓存都保存同一份直答判定，避免两次回答路径不一致。

可选插件参数：

```json
{
  "direct_answer_enabled": true,
  "direct_answer_min_similarity": 0.36,
  "direct_answer_min_support": 2,
  "direct_answer_score_gap": 0.03,
  "direct_answer_max_chars": 75
}
```

当前管理端知识库绑定只下发 RAGFlow 地址、密钥和数据集 ID，因此服务端使用上述保守默认值。未来若管理端透传这些参数，可按智能体覆盖；不需要修改直答代码。

| 中科生创有多少位科学家 | 热缓存直答 | 6 ms | 542 ms | 约 1.79 秒 |
| 详细介绍临床应用中心 | 热缓存 + LLM 归纳 | 8 ms + LLM 首 token 697 ms | 1110 ms | 约 2.61 秒 |

三项答案均正确；标准问答日志中 `action=RESPONSE` 且不存在 LLM 请求，详细问题日志中 `action=REQLLM`、策略为 `enterprise_explain`。标准 RAG 问答从此前约 3.1 秒 P50 降至约 1.8～2.1 秒开口。

## RAGFlow 连接复用与企业 FAQ 别名缓存

2026-07-29 在直答快路径之上增加两层冷/热链路优化：

1. `core/utils/ragflow_http.py` 为每个事件循环维护一个有界 `httpx` 连接池，最多 50 个连接、20 个 keep-alive 连接，空闲连接保留 30 秒；服务退出时由 `app.py` 统一关闭。连接失败或服务端关闭旧连接时只重试一次传输请求，不重试 HTTP 状态错误和超时，避免把故障放大成重复慢请求。
2. 第一次检索只有通过原有“精确问题或同答案共识、相似度、分差、长度”校验并得到直答后，才会写入 FAQ 别名缓存。后续同一字段的不同说法可以直接复用这条已验证答案，不再请求 RAGFlow，也不再请求 LLM。

别名缓存同时受 RAGFlow 地址、数据集 ID、分页/召回参数、检索阈值和直答阈值约束。知识库或关键参数不同不会串答案，TTL 默认与普通 RAG 缓存一致，当前为 600 秒。

当前只合并以下严格类别：

- 明确企业主体的电话；
- 明确企业主体的总部/公司地址；
- 明确企业主体的主营业务；
- 明确企业主体的科学家或专家数量；
- 严格短人名问句，且按姓名分别缓存。

人物电话、临床中心/实验室/基地地址、没有企业主体的模糊问题，以及包含“详细、介绍、为什么、如何、对比”等综合请求都不建立别名，继续走原检索和 LLM 路径。新增类别必须先证明不会把不同实体或字段合并，再修改 `build_enterprise_faq_cache_alias()` 并补边界测试；不允许只凭关键词扩展。

可单独关闭别名缓存进行回滚，不影响精确问句缓存与直答：

```json
{
  "direct_alias_cache_enabled": false
}
```

容器重启清空内存缓存后，在同一会话连续测试：

| 问题 | 路径 | RAGFlow | 首个 TTS 文本 |

| 查一下公司的电话 | 首次冷检索 | 745 ms，首次建连 | 1487 ms |
| 公司的联系电话是多少 | 电话别名命中 | 0 次请求 | 103 ms |

### 相邻链路清理：未绑定天气插件不再隐式预取

最终验收日志发现，企业电话问题虽然只路由到 RAG，但连接初始化的提示词增强逻辑仍会因为模板含 `weather_info` 而直接调用 `get_weather`。当管理端只绑定 RAG、没有给当前智能体下发天气插件配置时，旧代码会退回源码内的默认天气密钥，产生一次无关网络请求和认证错误。

现改为只有当前智能体的 `plugins.get_weather` 同时显式包含有效 `api_host`、`api_key` 时才预取天气上下文。未绑定天气不发请求；以后重新绑定并配置天气后，原天气上下文能力自动恢复。这项判断只影响提示词的天气预取，不改变轻量工具路由规则，也不修改管理端。

最终镜像回测中，企业电话冷查询和别名命中均未再出现 `get_weather` 请求或认证错误；冷检索本轮受 RAGFlow 波动为 1067 ms，别名命中工具耗时 4 ms、首个 TTS 文本 110 ms。该结果也再次说明冷链路要用多轮 P50/P95 评估，单次最低值不能当作稳定指标。
