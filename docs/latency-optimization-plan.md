# 语音链路低延迟开发与优化计划

> 状态：执行中  
> 适用范围：`main/xiaozhi-server` 的 VAD、ASR、LLM、Intent、TTS 与 WebSocket 音频链路  
> 配套记录模板：[performance-baseline-template.md](performance-baseline-template.md)

## 1. 目标与原则

本计划的目标是降低“用户说完话”到“客户端收到第一帧回复音频”的时间，并在并发、打断、工具调用和异常降级场景下保持稳定。最终是否达到或超过参考服务器，必须使用相同设备、网络、话术和统计口径进行 A/B 测试，不能用主观听感代替数据。

优化遵循以下原则：

1. 先建立可重复基线，再修改实现。
2. 一次实验只改变一个主要变量，记录 Git SHA、镜像摘要、配置和硬件。
3. 同时关注 P50、P95、P99、成功率与识别正确率，不能只看平均值。
4. 默认配置保持向后兼容；高风险优化必须有特性开关和回滚路径。
5. 日志与测试报告不得包含 API Key、Token、完整设备标识、用户原始音频或敏感对话。
6. 组件优化必须服从端到端结果，不能通过把耗时转移到下一阶段制造“局部变快”。

## 2. 当前状态快照

当前本地全模块 Docker 部署已经能够正常启动 OTA、WebSocket、MySQL 和 Redis。开发基线如下：

| 环节 | 当前实现 | 已知情况 |
| --- | --- | --- |
| VAD | Silero VAD | 阈值 `0.5`，静音结束阈值 `700 ms` |
| ASR | `fun_local` / SenseVoiceSmall | 本地 CPU 推理，语言为 `auto`，在检测到语音结束后才整段识别 |
| LLM | OpenAI 兼容接口 / Qwen3-30B-A3B AWQ | 远程推理地址；未显式配置输出上限等采样参数 |
| Intent | `function_call` | 当前启用音乐、新闻、天气 3 个插件，并额外注入 `direct_answer` 工具 |
| Memory | `nomem` | 不产生记忆查询耗时 |
| Prompt | 智能体系统提示词 | 当前约 284 个字符，聊天记录上报关闭 |
| TTS | `doubao` | 普通 HTTP 非流式接口；音色名含 `streaming` 不代表当前调用链是双向流式 |
| 运行方式 | 发布镜像 `server_latest` | 本地源码修改不会自动进入当前容器，需要建立开发镜像/挂载流程 |
| 真机 | 暂不可用 | 先做组件测试和协议回放，真机作为最终验收门禁 |

计划中的目标部署形态是让实时服务与模型推理解耦：

```text
ESP32 / 协议回放客户端
          |
          v
  xiaozhi-server
     |    |    |
     |    |    +--> 火山双向流式 TTS（云端对照组）
     |    +-------> Triton + CosyVoice（自部署实验组）
     +------------> 独立 FunASR 服务
          |
          +--------> OpenAI 兼容 Qwen 服务
```

ASR 保留“进程内 FunASR”作为对照和降级路径；TTS 保留“火山双流”作为云服务对照和自部署故障时的回退路径。切换通过 Provider 配置完成，业务主链路不包含厂商判断。

当前最值得优先验证的风险：

- VAD 固定带来约 700 ms 的尾部等待，是端到端延迟的一部分。
- `fun_local` 只有在 VAD 判停后才开始识别，ASR 与用户说话过程没有重叠。
- Qwen3 使用裸 IP 的 OpenAI 兼容地址；现有代码只按少数云厂商域名关闭思考模式，本地 Qwen3 可能先生成被过滤的隐藏思考 Token。
- 每轮 LLM 请求携带完整工具定义，增加 Prompt Token 和 Prefill 时间；普通问答也承担工具调用开销。
- 当前豆包 TTS 会等待一次 HTTP 请求返回完整 Base64 音频，再转码并发送，不是真正的首音频流式链路。
- ASR、TTS 和聊天处理混合使用每连接线程、线程池、同步 SDK 和异步事件循环；单连接可用，但并发扩大后线程数和上下文切换会成为瓶颈。
- 现有性能工具缺少统一分位数、冷/热启动、并发退化、端到端关联 ID；部分调试输出可能打印完整模型配置，需要先脱敏。

## 3. 统一延迟口径

所有时钟必须使用 `time.monotonic_ns()`，每轮对话生成唯一 `turn_id`，并在以下节点记录时间：

| 标记 | 事件 |
| --- | --- |
| `t0` | 检测到首个有效语音帧 |
| `t1` | 收到最后一个实际语音帧 |
| `t2` | VAD 判定语音结束 |
| `t3` | ASR 推理开始 |
| `t4` | ASR 最终文本产生 |
| `t5` | LLM 请求开始发送 |
| `t6` | 收到首个 SSE 数据块 |
| `t7` | 收到首个可展示、非思考内容 Token |
| `t8` | 第一段文本进入 TTS |
| `t9` | TTS 请求或会话开始 |
| `t10` | 收到 TTS 首个音频字节 |
| `t11` | 第一帧目标格式音频编码完成 |
| `t12` | 第一帧音频写入设备 WebSocket |

主要指标：

- VAD 尾延迟：`t2 - t1`
- ASR 最终结果延迟：`t4 - t3`
- LLM 首有效 Token：`t7 - t5`
- 首句切分等待：`t8 - t7`
- TTS 首音频：`t10 - t9`
- 编码与发送开销：`t12 - t10`
- 服务端首音频总延迟：`t12 - t1`
- 全链路响应：客户端记录的“松口/判停到扬声器开始播放”，待真机补测

每个场景至少包含 5 次预热和 30 次正式样本，报告 P50、P90、P95、P99、最大值、成功率。失败和超时必须进入成功率统计，不能从报告中静默剔除。

### 3.1 阶段性性能预算

下面是优化方向，不是当前实测结果。完成基线后可按硬件能力修订：

| 阶段 | P50 目标 | P95 目标 |
| --- | ---: | ---: |
| VAD 尾延迟 | 400–550 ms | ≤ 700 ms |
| 本地 ASR（2–4 秒短句） | ≤ 350 ms | ≤ 600 ms |
| LLM 首有效 Token | ≤ 400 ms | ≤ 800 ms |
| 首句切分等待 | ≤ 150 ms | ≤ 300 ms |
| 流式 TTS 首音频 | ≤ 300 ms | ≤ 600 ms |
| 编码与首次 WebSocket 写入 | ≤ 80 ms | ≤ 150 ms |
| 服务端首音频总延迟 | ≤ 1.5 s | ≤ 2.3 s |

最终目标应是在同一局域网和同一测试集下优于参考服务器，而不是追求某个脱离环境的绝对数字。

## 4. 没有 ESP32 时的测试方案

真机缺席期间仍可完成大部分定位工作：

1. **ASR 语料回放**：准备 1、3、5、10 秒中文 PCM/WAV，包含快语速、慢语速、尾部 200/400/700/1000 ms 静音和背景噪声。记录耗时、CER、内存与 CPU。
2. **LLM SSE 测试**：从 `xiaozhi-server` 容器发出与真实业务一致的 Prompt、历史和工具 Schema，分别记录首连接、首 SSE、首有效 Token、输出 Token/s 和输入 Token 数。
3. **TTS 测试**：使用 5、15、30、80 字文本，区分首次建连、复用连接、首音频和完整音频耗时，同时记录是否发生转码。
4. **协议回放**：使用项目的 `digital-human` 或新增最小 WebSocket 回放客户端，发送录制的 Opus 帧并接收回复音频，以覆盖 VAD→ASR→LLM→TTS→WebSocket 主路径。
5. **并发测试**：并发数按 1、5、10、20 递增，观察延迟分位数、线程数、队列长度、CPU、内存和错误率。
6. **真机补测**：设备可用后只补齐 Wi-Fi、固件缓冲、WebSocket 下行和扬声器开始播放时间，不推翻已有组件基线。

测试语料与配置中不得包含个人隐私。性能报告使用配套模板，原始音频和含密钥配置不提交到 Git。

## 5. 分阶段实施计划

### 阶段 A：可复现开发环境与可观测性

这是所有性能修改的前置条件。

#### DEV-001：建立源码开发镜像

- 新增开发 Compose 覆盖文件，服务端从当前工作区构建并使用明确的 Git SHA 标签，不能继续把 `server_latest` 当作开发镜像。
- 数据库、Redis、模型和用户上传目录继续复用现有持久卷。
- 配置与密钥只保存在忽略提交的本地文件中。
- 启动日志输出 Git SHA、镜像版本和配置摘要，不输出密钥。

验收：修改一行可识别日志后重建容器，容器内代码与当前 Git SHA 一致；切换回发布镜像只需一条 Compose 命令。

#### OBS-001：增加对话级结构化埋点

- 新增轻量 `TurnMetrics`，记录第 3 节定义的时间点。
- 日志统一包含 `session_id`、`turn_id`、provider 类型和阶段，不记录完整对话文本。
- 增加首有效 Token、首 TTS 音频、首 WebSocket 音频包三个当前缺失的关键点。
- 增加队列长度、线程数和阶段错误码。
- 埋点关闭时接近零开销；开启时单轮额外 CPU 时间目标小于 2 ms。

建议影响文件：

- `core/connection.py`
- `core/providers/asr/base.py`
- `core/providers/llm/openai/openai.py`
- `core/providers/tts/base.py`
- `core/handle/sendAudioHandle.py`

#### BENCH-001：重构性能测试入口

- 支持非交互命令行参数、固定随机种子和机器可读结果。
- 输出 P50/P90/P95/P99、错误率、冷/热启动和并发结果。
- 移除完整配置调试输出，对 Key、Token、Authorization 和设备 ID 统一脱敏。
- 为 ASR、LLM、TTS 使用同一份运行元数据和报告格式。
- 失败样本保留原因，不能仅统计成功样本平均值。

### 阶段 B：ASR 与端点检测

#### ASR-001：建立 FunASR 基线

- 对 `language=auto` 和 `language=zh` 做准确率与速度 A/B；纯中文场景优先考虑固定 `zh`。
- 分别测试冷启动、预热后单请求、连续请求和并发请求。
- 记录音频时长与推理耗时的 RTF，以及共享 `AutoModel` 在并发下的正确性。
- 服务器启动后执行一次无用户数据的短音频预热，避免首轮冷启动。

#### ASR-002：优化 VAD 判停

- 对 700、550、450、350 ms 做回放测试，不直接全量改成更激进的值。
- 验收同时关注截断率、误触发率、短停顿断句率和端到端延迟。
- 推荐先从 550 ms 灰度；若慢语速语料无回归，再测试 450 ms。
- 为自动、手动和 AEC 模式保留独立参数，不共用一个激进阈值。

#### ASR-003：消除本地推理阻塞与无界竞争

- 将本地模型推理放入专用、容量受控的 Executor，不使用默认全局线程池。
- 增加并发信号量和排队时间指标，避免多个连接同时调用同一模型导致抖动或内存峰值。
- 将异常重试中的 `time.sleep()` 改为非阻塞等待。
- 验证 FunASR 模型线程安全性；若不安全，单模型串行或建立受控实例池。

#### ASR-004：评估真正的流式 ASR

- 当前 `fun_local` 和 `fun_server` 都是在语音结束后处理整段音频；不要仅因使用 WebSocket 就标记为流式。
- 评估 FunASR online/2pass Provider，在说话过程中持续送帧，结束时只等待最终修正。
- 以“准确率不下降、P95 明显改善”为上线门槛；若流式方案收益不足，保留本地非流式作为稳定回退。

#### ASR-005：独立部署 FunASR

- FunASR 使用独立容器/服务部署，模型版本、运行时镜像和热词文件全部固定版本，不与 `xiaozhi-server` Python 依赖混装。
- 当前项目的 `fun_server` 每轮建立 WebSocket，发送 `mode=offline` 的整段 PCM；它只能作为“独立非流式 FunASR”基线，不能代表在线 2pass 的性能。
- 新增独立 Provider，例如 `fun_server_2pass`，支持连接复用、音频逐帧上送、最终结果、取消、超时和服务端健康检查。
- Provider 记录客户端排队、建连、上传、服务端推理和最终结果等待，避免把网络时间算成模型推理时间。
- 独立服务设置有界并发与明确过载响应；模型异常时可按配置回退 `fun_local`，但禁止同一请求静默双跑造成资源放大。
- 部署时优先与 `xiaozhi-server` 同机或同内网。若跨公网，单独记录 RTT、抖动和丢包，结果不能与进程内模式直接比较。

必须完成三组 A/B：

| 方案 | 用途 | 重点指标 |
| --- | --- | --- |
| `fun_local` | 当前基线/回退 | 推理耗时、CPU、并发安全 |
| 独立 FunASR offline | 验证进程解耦成本 | 网络增量、隔离性、部署稳定性 |
| 独立 FunASR online/2pass | 低延迟候选 | 最终文本延迟、CER、断句和连接稳定性 |

### 阶段 C：LLM 首有效 Token

#### LLM-001：显式关闭 Qwen3 思考模式

- 先确认推理后端是 vLLM、SGLang、Xinference 还是其他实现，并记录版本、启动参数、GPU 与 Chat Template。
- 不再仅依赖域名判断；增加配置驱动的 `enable_thinking`/`extra_body` 支持。
- 分别记录首 SSE 和首个过滤掉 `<think>` 后的有效 Token，确认是否存在隐藏思考耗时。
- 修改必须兼容不支持该参数的 OpenAI 服务，并提供关闭开关。

这是当前 LLM 最高优先级验证项。

#### LLM-002：控制 Prompt 与工具开销

- 记录系统提示词、历史、工具 Schema 各自的 Token 数。
- 普通聊天对比 `function_call` 与 `nointent` 的 TTFT；当前只有 3 个插件，也要以数据决定是否优化。
- 实现轻量本地工具路由：只有天气、新闻、音乐等候选请求才注入相关工具；无法确定时回退完整工具集。
- 保证工具顺序和系统前缀稳定，使推理服务的 Prefix Cache 可命中。
- 对历史消息设置 Token 预算，不按轮数无限增长。

#### LLM-003：请求参数与连接复用

- 为语音短回答设置合理 `max_tokens`，建议从 128/256 A/B 开始；不能用过大输出上限拖高尾延迟。
- 固定适合口语回答的温度和 `top_p`，避免每个智能体依赖未声明的后端默认值。
- 对连接、读、写和连接池分别设置超时，异常时快速播放降级提示。
- 验证 HTTP Keep-Alive 和连接池命中；避免每台设备、每轮对话重复 TLS/TCP 建连。
- 中期将同步 `OpenAI` SDK 和线程内生成器迁移为 `AsyncOpenAI`，减少每连接线程池与上下文切换。

#### LLM-004：推理服务专项调优

拿到推理后端和 GPU 信息后再确定参数，重点检查：

- 模型是否在请求前完成权重、CUDA Graph 和 Kernel 预热。
- Prefix Cache、Chunked Prefill、KV Cache 和最大上下文是否配置合理。
- AWQ Kernel 是否与 GPU 架构匹配，有无 CPU Offload。
- 单请求低延迟与并发吞吐使用不同配置档，不用一个参数集兼顾所有场景。
- 多 GPU Tensor Parallel 是否因卡间通信反而增加单请求 TTFT。
- 只有在基线稳定后才评估投机解码，且必须验证回答质量和工具调用格式。

### 阶段 D：TTS 首音频

#### TTS-001：切换火山双向流式 TTS

- 先确认账号、资源 ID 和音色支持 `huoshan_double_stream`。
- 与当前普通 `doubao` 做相同文本、相同次数的 A/B，分别测首音频和完整音频。
- 开启 WebSocket 复用并验证空闲超时、断线重连和并发额度。
- 保留普通 HTTP Provider 作为运行时降级方案。

这是当前最可能获得最大用户可感知收益的配置变更。

#### TTS-002：优化首段文本切分

- 当前非流式路径通常等待逗号或句末标点后才发起 TTS。
- 增加“标点、最大首段字符数、最大等待时间”组合策略，例如首段 10–18 个汉字或等待 150–250 ms 后刷新；具体值通过自然度 A/B 决定。
- 数字、日期、英文缩写和 Markdown 清理必须保持原有正确性。
- 双向流式 Provider 优先增量送文本，不重复创建每句会话。

#### TTS-003：减少网络和转码成本

- 优先请求服务端直接返回客户端可接受的采样率与编码，减少 WAV/Base64/PCM/Opus 多次转换。
- 记录 `首音频字节→首 Opus 帧` 的独立耗时。
- 普通 HTTP 回退 Provider 使用持久 Session、明确超时和有限重试；当前最多 5 次重试不能阻塞低延迟主路径过久。
- 复用 Opus 编码器，但验证其线程归属和并发安全。

#### TTS-004：部署 Triton + CosyVoice 并建立公平对照

- 基于 CosyVoice 官方 `runtime/triton_trtllm` 路径部署，固定 CosyVoice 模型版本、官方仓库 Commit、Triton/TensorRT-LLM 镜像、Engine 构建参数和 GPU 型号。
- 官方运行时目前覆盖 CosyVoice2 + UNet、CosyVoice2 + DiT 和 CosyVoice3 等路径。第一轮只选择一个稳定版本，禁止同时更换模型、Token2Wav 和客户端切句策略。
- 新增 `triton_cosyvoice` Provider，遵循现有 TTS Provider 接口，对外提供真正的增量音频回调、取消、超时、健康检查和降级。
- 如果模型使用 Triton decoupled 多响应模式，客户端必须使用双向流式 gRPC；普通 HTTP/一元 RPC 不能承载同一请求的多个流式响应。
- gRPC Channel 按服务级复用，每轮请求使用唯一 ID；打断时取消对应请求，不能关闭其他设备共享的 Channel。
- 对音频 Chunk 设置有界队列和背压，防止模型输出快于 WebSocket 下游时内存持续增长。
- 分别建立“单请求低延迟”和“并发吞吐”两套 Triton 配置。Dynamic Batching、Instance Count 和队列等待必须通过数据调整，不能默认认为批处理一定更快。

火山双流与 Triton/CosyVoice 的对比矩阵：

| 维度 | 火山双向流式 | Triton + CosyVoice |
| --- | --- | --- |
| 首音频与 P95/P99 | 必测 | 必测 |
| 完整音频 RTF | 必测 | 必测 |
| 1/4/8/16 并发退化 | 受账号并发额度影响 | 受 GPU、实例数和队列影响 |
| 网络 RTT/抖动 | 公网单独记录 | 同机/内网单独记录 |
| 音质与韵律 | 主观盲测 + ASR 回识别 | 主观盲测 + ASR 回识别 |
| 音色一致性 | 使用固定云音色 | 固定 SFT/零样本音色与参考音频 |
| 可用性 | 超时、限流、断线 | OOM、模型未就绪、Engine 异常 |
| 成本 | 字符/调用费用 | GPU、显存、电力和运维 |
| 数据边界 | 音频发往云端 | 可完全留在自有环境 |

公平性要求：

1. 两组使用相同输入文本、首段切分策略、目标采样率和 Opus 帧长。
2. “速度对比”与“音质对比”分开报告，因为不同音色无法做到严格同源。
3. 同时报告冷启动和热连接；CosyVoice Engine 构建/模型加载时间不混入热请求延迟，但必须单独记录恢复时间。
4. 每个并发档至少 30 次正式请求，不能只比较最佳单次结果。
5. CosyVoice 若启用零样本克隆，参考音频预处理和 Speaker Embedding 缓存策略必须固定并记录。

### 阶段 E：主链路调度与并发

#### CORE-001：减少每连接线程

当前单连接至少会创建 ASR 线程、TTS 文本线程、TTS 播放线程和最多 5 个工作线程。计划逐步改为：

- WebSocket 收包进入有界 `asyncio.Queue`。
- I/O Provider 使用原生异步客户端。
- CPU 推理进入全局受控 Executor/Worker Pool。
- 队列满时执行明确的丢弃、背压或拒绝策略，并记录指标。
- 保持同一连接内消息有序，打断操作能够取消旧轮次任务。

验收：并发 20 连接时线程数不随“每连接固定 8 个左右”线性增长；P95 不出现明显阶跃。

#### CORE-002：配置缓存与 Provider 生命周期

- 缓存设备配置并按版本/更新时间失效，减少重连时 Manager API 查询和 Provider 重建。
- 对可安全共享的 VAD、ASR、HTTP 连接池和模型实例使用进程级生命周期。
- 含会话状态的 TTS/流式 ASR 连接仍按设备隔离，不能错误共享。
- 服务器启动完成后执行健康检查和预热，再对外标记 Ready。

#### CORE-003：部署拓扑优化

- 性能验收时让 `xiaozhi-server` 与 Qwen 推理服务尽量同机房或同内网，单独记录网络 RTT。
- 本地开发、固定局域网真机测试和公网 FRP 入口分别建立配置档，不能混用测试结果。
- Docker 资源限制、CPU 架构和虚拟化环境必须写入报告；Mac Docker 的结果不能直接代表 Linux GPU 生产服务器。

## 8. 项目开发规范

仓库当前没有统一 Python Lint 或完整服务端单元测试门禁，因此性能开发新增以下约束：

1. Python 以项目要求的 3.10 和锁定依赖版本为准，不在性能提交中顺便升级基础依赖。
2. 新 Provider 继续遵循 `core/providers/<type>/` 的 Provider 模式，公共流程放基类，厂商协议留在子类。
3. 配置新增项必须提供默认值、注释和旧配置兼容；Manager API 与 Server 分两步发布时也能正常工作。
4. CPU 阻塞任务不得直接运行在 WebSocket 事件循环；异步函数内不得使用 `time.sleep()` 或无超时网络请求。
5. 队列、线程、连接池和后台任务必须有容量、退出和异常清理逻辑。
6. 使用小提交和明确范围，推荐提交类型：`perf(server):`、`refactor(server):`、`test(server):`、`docs(perf):`。
7. 每个性能合并请求必须附配套基线记录，包含假设、前后数据、质量检查和回滚方法。
8. 纯重构与性能参数调整分开提交，便于二分定位和回滚。
9. 不修改或提交 `deploy/` 中的用户数据库、模型、上传文件和密钥；开发 Compose 使用模板与本地覆盖文件分离。
